# Hardware checklist — what no emulator can prove

For the operator, on the reference phone (OPPO Find X9 Ultra, ColorOS) with the TH-D75A. Each row
is a test-plan §7 device test: a written protocol, a **prediction recorded before the run**, and a
result file at `results/e2e-audit/hardware/H<n>.md` carrying the device, build hash, date and what
happened (constitution II: an unrecorded manual test did not happen). Run them once the packages
in [`../../spec/e2e-capture-modes-plan.md`](../../spec/e2e-capture-modes-plan.md) have merged and
the checklist rows they depend on read `closed` on the emulator.

**Before every row:** `install.ps1 -Clear`-equivalent on the phone (`adb shell pm clear org.ort.app`,
re-grant `RECORD_AUDIO` and `POST_NOTIFICATIONS`), note `git log -1` of the build.

| H | Test | Steps | Prediction (recorded 2026-09-10) | Criteria |
|---|---|---|---|---|
| **H1** | TH-D75A over **USB serial** | Radio on, USB-C to the data port. Setup: mode *USB-connected radio* → S04 pick the USB audio adapter → verify → S09 TH-D75A → S09b USB serial → S10 grant the OS prompt → S11. Then change the frequency on band A on the radio; watch N04. | S10 identifies the rig by `ID`; S11 lists FQ BY FO AI BL verified; N04 shows both bands; a frequency change on the radio reaches N04 within 2 s via `AI` push without polling. CDC-ACM claims with no driver. | D15, AC-133 (USB half), FR-RIG-3 |
| **H2** | TH-D75A over **Bluetooth SPP** | Radio: Menu › Bluetooth › On; pair it in Android Bluetooth settings. Setup: mode *Bluetooth-connected radio* → S02c allow → S04 pick the **USB audio adapter** (audio stays cabled) → S09 TH-D75A → S09b Bluetooth SPP → S10b pick TH-D75A → wait for identify/verify → S11. Repeat H1's frequency change. | S10b shows the radio with `serial port profile`; the link opens in under 2 s; S11 shows the **same** verified command set as H1 and the same capabilities (parity); `AI` push works over SPP. Kenwood's own MCP-D75/ARFC-D75 use this path. | AC-133, FR-RIG-14 |
| **H3** | **Bluetooth rig link drop** | From H2, capturing. Power the radio off for 60 s, then on. | Within 10 s F9 appears naming Bluetooth; the frequency column carries `?`; the live bar reads *Rig lost*; capture continues (overs keep arriving from the cabled audio). On power-up the link reconnects on its own within the backoff ladder; the "Radio reconnected" toast fires; later overs lose the `?`. No gap is recorded (audio never stopped). | FR-RIG-15, FR-RIG-7, AC-133 |
| **H4** | **USB re-plug** mid-session | From H1, capturing. Pull the USB-C cable for 10 s, reinsert. | F16 surfaces loudly (permission lost on re-attach); `Grant again` reopens the OS prompt; until granted, the frequency reads stale; capture continues if the audio adapter is on a different cable, or records a gap if it was the same cable — and says which. | D10, F16, FR-PLT-2 |
| **H5** | **Bluetooth audio from a headset-class device** | Any Bluetooth headset with a microphone (or a headset-profile adapter on the radio's speaker jack), paired. Setup: mode *Bluetooth-connected radio* → S04 pick the headset → verify → continue as H2. Capture a few overs with the headset mic at the radio's speaker. | S04 lists it as `Bluetooth · 16 kHz mSBC` (or CVSD) with the narrowband disclosure; S05 passes; N04 and DG04 show the negotiated profile; every over row carries `bt audio`; the audio is audibly narrowband. Session row `bluetoothProfile` is set. | AC-132, FR-CAP-11, FR-CAP-13 |
| **H6** | **TH-D75A itself as the Bluetooth audio source** | With the radio paired (H2), open S04 and `Refresh`. Look for the TH-D75A among the audio routes. If it is absent, open Android Bluetooth settings for the TH-D75A and note which profiles it offers. | **Predicted: not offered.** Android plays only the HFP audio-gateway role and the TH-D75A is also an audio gateway (it connects *to* headsets), so no input route appears. If a route *does* appear — some OEM stacks enable HFP client — record the profile it negotiated and whether S05 hears signal; that result amends the FR-CAP-11 note in the spec either way. | D34 note, FR-CAP-11 |
| **H7** | **Bluetooth audio drop** mid-session | From H5, capturing. Switch the headset off for 90 s, then on. | Within 5 s F23 appears; the live bar reads *Input lost*; a gap row opens in the Log and grows; the retry ladder counts; on power-up the route re-verifies, the gap closes with its true length, capture resumes; `Switch to a wired input` opens S04. Nothing was captured during the gap and the record says so. | FR-CAP-5, F23, FR-RUN-12 |
| **H8** | **Mode change while capturing** | Capturing in any mode. Settings › Input and level › Capture mode → pick a different mode → confirm. Open DG04 for the running session. Stop capture. Start a new session. | CF11 shows the amber "applies when it ends" banner; the running session's DG04 still shows the original mode; the next session's N04 and DG04 show the new mode; no record changed. | AC-131, FR-CAP-12 |

| **H10** | **Corrupted bundled asset** (optional on hardware; required on the AVD via `asset-corrupt`) | Debug build: `adb shell run-as org.ort.app sh -c 'printf x >> files/models/tiny.en-encoder.int8.onnx'`; relaunch. | Launch verification fails for that file; the app states which asset failed and what it is doing (fallback tier, `Reinstall from bundle` action); nothing activates the corrupt file; `Reinstall` restores it from the bundle and verifies. | AC-137, FR-AST-3b |
| **H11** | **LLM at tier 3** | Settings › Models › *Write prose summaries* on. Capture a session with at least one multi-over thread. Stop. Plug in the charger, leave the phone idle 20 min. Open the digest. Then turn the toggle off and check Settings › Diagnostics (resident memory). | Prose appears only after the idle-and-charging window, badged `generated`, italic, each card citing its overs; no summary names a callsign absent from the deterministic digest; while capturing, no prose is generated (check the digest mid-session); turning the toggle off releases the model's memory (resident set drops by roughly the model size). On a tier-0/1 phone, if available: the model is listed as stored and never loaded. | AC-87, AC-138, AC-140, FR-DIG-4/5/6 |
| **H12** | **Local-microphone overnight** | Mode *Local microphone*. Phone on the desk beside the TH-D75A speaker, squelch set on the radio. Capture overnight. | Every screen with the live bar shows the `room` mark and N01 the room-audio chip; DG04 reads *Local microphone · room audio*; overs transcribe with room noise present; the session is reported as its own source in any accuracy tally. | AC-128, AC-129, FR-CAP-10 |
| **H13** | **Eight-hour run** in USB-radio and Bluetooth-radio modes | The D4 protocol from test-plan §7, once per mode, with ColorOS interventions applied. | Capture survives in both; the Bluetooth SPP link may drop and must reconnect on its own without a gap in audio — **prediction unknown for ColorOS's Bluetooth power policy; record it.** | AC-64, R5, FR-RIG-15 |
| **H14** | **Ghost text at font scale 2.0** | On the real device, set font scale to the largest system setting, open the rig-transport step (S09b: mode *Bluetooth radio*, TH-D75A chosen) and the settings screens, and photograph or screenshot the top of the frame. | The emulator's software renderer draws a faint second "Back" over the status-bar area on S09b (register R-884; the same class as R-220/R-280/R-340/R-612 in the UI conformance program). **Prediction: absent on real hardware** — if it appears, it is a product defect and R-884 reopens. | R-884, guide §5 |
| **H15** | **Upgrade over an older install** | On the real device, do not clear data: install this build over whatever version is on the phone, launch, open Earlier nights, then pull the database (`adb backup` or `run-as … cat databases/ort.db`) and read `PRAGMA user_version` and `PRAGMA table_info(session)`. | Register R-885: builds before `8c7e5f0c` crashed on the first open after an upgrade (`migrate(SQLiteConnection)` not implemented), and Room wraps no outer transaction around a multi-statement migration, so a phone that crashed mid-migration may hold a half-applied version. **Prediction: a phone that never ran a pre-fix build upgrades cleanly to version 10 with every v7–v10 session column present; a phone that did crash needs this check and, if a column is missing, the app must refuse to open the database rather than run on it** — report what `user_version` and the column list say. | R-885, AC-5, FR-PLT-1 |
