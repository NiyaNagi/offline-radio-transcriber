# Audit-and-remediate prompt (Fable finds, Sonnet fixes)

Paste the whole of the section below as a single prompt to a **Fable** session running in this
repository. It is written to be token-frugal: Fable does judgment, Sonnet subagents do reading,
evidence-gathering and fixing.

---

## Your role

You are auditing the `offline-radio-transcriber` repository against its own specification and
build plan, producing a durable register of every real defect and gap, and then having those
fixed — one at a time, verifiably — by Sonnet subagents that you dispatch.

**You find. You judge. You verify. You do not fix.** Every code change is made by a Sonnet
subagent you dispatch with a precise, single-issue brief. The only files you edit yourself are
the audit register and the changelog entry for the audit itself.

**Token discipline is a hard requirement.** You are the expensive model in this arrangement, and
the repository is large: a 266-requirement functional spec, 419 requirement ids, ~20 Gradle
modules, and a changelog with 41 entries. If you read it all yourself the audit will cost more
than it is worth and will run out of context before it finishes. The rules in "How to spend your
context" below are not suggestions.

---

## Read these first, in this order, and nothing else yet

1. `.specify/memory/constitution.md` — binding, short. The non-negotiables are the highest-value
   defects to find, because breaching one is always a real bug even when tests pass.
2. `AGENTS.md` — the working agreement, module boundaries, domain vocabulary, and the list of
   rules "an agent is most likely to breach by being helpful."
3. `spec/build-plan.md`, **the Progress section only** (stop at "## The prompts"). It carries
   per-prompt completion state and, for the incomplete ones, an explicit note of what remains.
4. `results/coverage-matrix.md`, **the header table only** (first ~15 lines). Generated by
   `./gradlew coverageMatrix`. Today: 419 requirement ids, 101 covered by ≥1 test, 318 uncovered.

Then run these two commands and read their output — both are cheap and high-signal:

```
python tools/spec-check/spec_check.py
./gradlew build dependencyRules
```

Do **not** read `spec/functional-spec.md`, `spec/technical-design.md` or `CHANGELOG.md` end to
end. They are large. Target them with `Grep` for specific ids and headings when a finding needs
adjudicating.

---

## The single highest-yield source, use it first

This project's changelog convention requires every entry to end with a **"Left open / not done"**
paragraph. There are currently **41 of them**, and together they are a pre-written, author-honest
inventory of every known gap — written by the session that created each gap, at the moment it
created it.

Harvest them in one cheap pass:

```
grep -n -A 6 "^\*\*Left open" CHANGELOG.md
```

Most of your register will come from this. Treat each as a *candidate* finding, not a confirmed
one: some have since been fixed by later work, and your job includes checking which.

---

## What counts as a finding, and what does not

This project defers work deliberately and records it honestly. **A documented, deliberate
deferral is not a defect.** Do not pad the register.

**These are findings:**

| Class | Definition |
|---|---|
| **A. Broken** | Code that does not do what it claims. Wrong behaviour, a crash, a wiring gap between two individually-green modules. |
| **B. Silently wrong** | Behaviour that looks correct and is not — a fabricated value, an optimistic constant, a state that reports success when it failed. **Weight these highest.** The constitution exists because this product's characteristic failures are silent. |
| **C. Constitution breach** | Anything violating `.specify/memory/constitution.md` or AGENTS.md's "Rules that are not negotiable", whether or not a test catches it. |
| **D. Spec divergence, unrecorded** | Implemented differently from the spec, with no decision or changelog entry recording the divergence. (A *recorded* divergence is class F.) |
| **E. Claimed-done, not done** | A build-plan item checked off, or a changelog entry claiming a requirement holds, where the code or test does not actually establish it. |
| **F. Recorded gap, still open** | An honest deferral that is now unblocked and should be closed. Real work, lower urgency. |

**These are not findings — classify and set aside:**

- **G. Blocked on the physical world.** Needs the reference device, the Fearless Steps
  registration, or the user's own recorded validation hour / noise tape. Includes P9's device
  matrix, AC-6, AC-64, R4, and M3's real dev-fold numbers. List them in the register under
  "Cannot be closed here" and move on. **Never fabricate a number or a verdict to close one.**
- **H. Unbuilt future milestone.** M6 (identity/voice library), M7 (rig), M8 (streaming), M9
  (digest/station knowledge/contribution), M10 (tiers/reprocessing), M11 (reference levers), and
  the M4 fork decision. These are not defects; the plan defers them on purpose. Produce a
  **separate, short scoping note** for these — do not build them and do not silently skip them.

## How to spend your context

- **Delegate all bulk reading.** When a finding needs evidence from code you have not read, spawn
  a Sonnet `Explore` subagent with a narrow question ("Does anything construct `X` in production
  code, or only in tests? Answer with file:line evidence."). Batch several such questions into
  one agent where they are related. You read the answer, not the files.
- **Grep before you read.** `Grep` for a requirement id, a class name, or a `TODO` before opening
  anything. Read specific line ranges, never whole large files.
- **Use the generated artefacts.** `results/coverage-matrix.md` already tells you which
  requirement ids have no test. Do not re-derive that by hand.
- **Do not re-verify what the tooling verifies.** `./gradlew build dependencyRules` covers module
  boundaries, lint, detekt and every unit test. `spec_check.py` covers spec integrity. Run them;
  trust them; spend your attention on what they cannot see.
- **Never read a subagent's transcript file.** It will blow your context. Read only the report it
  returns.

## Task 1 — Build the register

Create `results/audit-2026-09-XX.md` (use today's date). This file is the durable spine of the
work: if your context is lost, the next session must be able to resume from it alone.

One row per finding, each **independently fixable and independently verifiable**:

```
### F-001 — <one-line summary>
- **Class:** A/B/C/D/E/F (or G/H for the set-aside sections)
- **Evidence:** file:line, or the command and its output. Never "it seems".
- **Requirement/principle:** the id it breaches (FR-*, AC-*, constitution principle), or "none — internal".
- **Owning module(s):** which Gradle module(s) a fix touches. This determines what can run in parallel.
- **Fix sketch:** one or two sentences. Not a design document.
- **Verification:** the exact command or test that will prove it fixed.
- **Status:** OPEN
```

Granularity rule: if a fix would touch more than two modules, or would need two unrelated tests,
split it into separate findings.

**Cover at minimum these axes.** For each, say explicitly in the register what you checked, even
where you found nothing — a clean axis is a result.

1. **Constitution non-negotiables.** Walk AGENTS.md's "Rules that are not negotiable" list one by
   one. For each, find the code that enforces it and confirm the enforcement is real. (`:capture-*`
   never depends on `:asr-*`/`:lexicon`/`:identity`; only `:net` links an HTTP client; the
   segmenter takes no `Tier`; `CONFIRMED` never promoted from a voice match; an attribution
   without its state is a bug at the data layer; nothing deleted quietly; the `eval` fold sealed.)
2. **Wiring gaps.** The recurring defect class in this repo: two modules each green, nothing
   joining them. Ask of every major capability — is it *constructed* in production code, or only
   in tests? Known live example to confirm and close: `:net`'s `ModelAcquisition` has no `:app`
   call site, so no ASR/VAD model ever reaches the device and transcripts cannot appear.
3. **Claimed-vs-actual.** For each build-plan item marked `[x]`, spot-check that its headline
   acceptance criteria are genuinely established by a test, not merely mentioned. Prioritise
   P12–P18 (Wave E) — the newest and least-reviewed.
4. **Silent-failure sweep.** Grep for optimistic constants and swallowed failures in the paths
   that report status: hardcoded `true`, empty `catch`, a default that masks absence. Two of this
   exact class have already been found and fixed in this repo (`isCapturing = true`; a fabricated
   device id); assume there are more.
5. **Design fidelity.** `design/canvas/` has seven artboards and `canvas.json` describing them.
   Compare each implemented screen against its artboard. Named, recorded divergences (there are
   several) are class F at most; *unrecorded* ones are class D.
6. **Requirement coverage triage.** 318 requirement ids have no test. Do not file 318 findings.
   Instead: identify which of those ids belong to **already-built** capability (those are real
   gaps — class E or F) versus unbuilt milestones (class H). File the former, in grouped findings
   by family, and give a count for the latter.
7. **Test integrity.** Are any tests asserting nothing, skipped without being reported, or named
   for a requirement they do not establish? (One known-good pattern to respect: the FTS5 test is
   `Assume`-skipped *deliberately and honestly* because Robolectric lacks the module — that is
   correct behaviour, not a finding.)

Order the register by severity: class B and C first, then A, then E, then D, then F.

## Task 2 — Confirm the register with the user before fixing

Post a short summary: counts by class, the five most serious findings in one line each, the
"cannot be closed here" list, and the milestone scoping note. **Then stop and wait.** Do not begin
dispatching fixes until the user responds — the register is where a wrong judgment is cheap to
correct, and after fixes begin it is not.

---

## Task 3 — Fix, one finding at a time, with Sonnet subagents

Work down the register in severity order. For each finding, dispatch **one Sonnet subagent for
one finding**. Never give an agent two findings.

Each brief must contain, and nothing much more:

- The finding's id, evidence and requirement, copied verbatim from the register.
- The standing preamble from `spec/build-plan.md` (constitution check, strict TDD — test first and
  seen to fail for the right reason, behavioural fake in the same change, stop rather than
  half-finish, append a `CHANGELOG.md` entry in the documented format before committing).
- **Owns / Do not touch**, explicitly, by module. This is what keeps parallel agents from
  colliding and is the discipline that has held all through this project.
- The exact verification command that closes the finding.
- The instruction to commit with a message prefixed `audit F-0NN ·`, ending with the repository's
  current attribution line.
- An explicit instruction: **if the fix turns out to be wrong, bigger than described, or blocked,
  stop and report — do not improvise scope.** A subagent that reports "this is actually two
  problems" is doing its job.

**Parallelism:** you may run several agents at once **only** when their owning modules are
disjoint. `:app` is the busiest module in this repo — treat two `:app` findings as serial unless
they are in clearly separate packages. When in doubt, serialise; the merge conflicts are not
worth the wall-clock saving.

**Isolation:** dispatch with `isolation: "worktree"`. After each agent returns, you merge its
branch into `main` yourself, resolve any conflict, and run:

```
./gradlew build dependencyRules
python tools/spec-check/spec_check.py
```

Both must be green before you dispatch the next fix. Then mark the finding `FIXED — <commit>` in
the register and push.

---

## Task 4 — Close out

When the register has no OPEN findings in classes A–E:

1. Regenerate `./gradlew coverageMatrix` and record the before/after numbers.
2. Write one `CHANGELOG.md` entry for the audit as a whole: what was checked, what was found by
   class, what was fixed, and **what remains open and why** — with the class G and H lists intact,
   because those are the honest answer to "is it complete?".
3. Update `spec/build-plan.md`'s progress notes where a fix changes an item's real status.
4. Report to the user: findings by class, fixes landed, what still cannot be closed without
   hardware/registration/recording, and the milestone scoping note for M6–M11.

## Repository facts that will save you time

- **Build commands.** `./gradlew build dependencyRules` (everything), `./gradlew coverageMatrix`,
  `python tools/spec-check/spec_check.py`, `cd corpus && python -m pytest`.
- **`JAVA_HOME` is wrong in every fresh shell** — it points at a JRE 8 and Gradle fails
  immediately with a toolchain-capability error. Set it per command:
  `$env:JAVA_HOME="C:\Program Files\Eclipse Adoptium\jdk-17.0.20.101-hotspot"`, and for anything
  touching Android modules also `$env:ANDROID_HOME="$env:LOCALAPPDATA\Android\Sdk"` and
  `$env:ANDROID_SDK_ROOT="$env:LOCALAPPDATA\Android\Sdk"`.
- **Shell is PowerShell.** No `&&`, no heredocs. For a multi-line commit message, write it to a
  file and use `git commit -F <file>` — inline `-m` with quotes and newlines will be mangled.
- **Ignore `.claude/`** — agent worktrees live there and are gitignored.
- **Merge conflicts are almost always in `CHANGELOG.md` and `spec/build-plan.md`**, because every
  agent appends to both. They are nearly always additive unions — keep both sides. `spec_check.py`
  check 8 will catch a marker you miss.
- **A model file is ~100 MB and must never be committed.** `asr-sherpa/README.md` documents the
  URLs and cache layout.
- **Nothing in this repository has ever been verified on a physical device.** Every UI and capture
  behaviour is Robolectric-only. Say so wherever it matters; do not let a fix claim otherwise.

## The standard you are holding this to

The constitution's framing is the right one: *this product's characteristic failures are silent.*
A capture that quietly records the room instead of the radio, a status screen that says
"Capturing" when nothing is, an attribution presented without its confidence, a number reported
without its fold — each looks fine and is wrong. Those are the defects worth your attention.
Cosmetic inconsistencies are not, unless the spec names them.

And the rule that governs your own output as much as the code's: **if something cannot be
verified here, say so plainly rather than closing it.** An honest register with open items is
worth far more than a complete-looking one that quietly asserts what was never checked.
